# ACP acceptance scenario — ветка `feat/acp-plan-updates`

Сценарий проверяет новое поведение ветки на реальной модели и присылает готовый отчёт.
Его можно целиком отдать агенту в BB: он запускает два режима, читает `report.md` и
прикладывает отчёт.

## Что проверяется

| ID | Проверка | Что доказывает |
|---|---|---|
| T1 | `initialize` рекламирует `list`, `resume`, `fork`, `close` | capability `session/fork` действительно опубликована |
| T2 | `session/new` + реальный `session/prompt` | базовый цикл работает, ход завершается `end_turn` |
| T3 | `session/fork` на **живой** сессии | форк через flush + чтение durable-лога |
| T4 | промпт в форке просит код-слово из исходной сессии | форк унаследовал завершённый диалог |
| T5 | `session/close` исходной сессии | закрытие не ломает последующие операции |
| T6 | `session/list` после закрытия | в `SessionInfo` приходит непустой `title` из кэша проекций |
| T7 | `session/fork` на **закрытой** сессии | форк из storage без живого агента |
| T8 | `session/resume` закрытой сессии | resume по-прежнему возвращает config options |
| T9 | `session/fork` с чужим `cwd` | отказ `cwd does not match` |
| T10 | `session/fork` сессии без завершённого хода | отказ `session has no completed turn` |
| T11 | `session/new` с недоступным MCP-сервером | ошибка, сервер не публикует сессию |
| T12 | `session/delete` закрытой сессии | сессия исчезает из `session/list`, повторное удаление даёт `not deletable` |
| T13 | `session/delete` активной сессии | отказ `is active`, сессия остаётся рабочей |
| T14 | `session/load` закрытой сессии | история (user + assistant) приходит до ответа, config options на месте |

Промптов к модели всего два (T2 и T4), поэтому полный прогон занимает ~1–3 минуты
плюс время старта сервера из исходников.

## Предусловия

- Репозиторий на ветке `feat/acp-plan-updates`, `pnpm install` уже выполнен.
- Node.js >= 24.9.
- В окружении есть `DEEPSEEK_API_KEY` (BB уже работает через ACP, значит ключ есть).
  Ключ **не** печатать и не прикладывать к отчёту.
- Запуск из корня репозитория. Сервер поднимается из исходников
  (`node --import tsx/esm apps/cli/src/bin.ts --profile acp`), отдельная сборка не нужна.
- Драйвер создаёт собственный временный `DSH_HOME` и рабочую папку, поэтому личные
  сессии и настройки не затрагиваются.

## Как запускать

Сначала быстрый smoke без вызовов модели (проверяет транспорт, capability и отказы):

```sh
ACP_ACCEPTANCE_SMOKE=1 node packages/acp/acp/acceptance/driver.mjs
```

Затем полный прогон с реальной моделью:

```sh
node packages/acp/acp/acceptance/driver.mjs
```

PowerShell:

```powershell
$env:ACP_ACCEPTANCE_SMOKE='1'; node packages/acp/acp/acceptance/driver.mjs
Remove-Item Env:ACP_ACCEPTANCE_SMOKE
node packages/acp/acp/acceptance/driver.mjs
```

Опции:

- `ACP_ACCEPTANCE_KEEP=1` — оставить временные `DSH_HOME` и workspace для разбора.
- `ACP_ACCEPTANCE_TIMEOUT_MS=900000` — увеличить общий таймаут (по умолчанию 10 минут).

## Что должно получиться

Полный прогон: **все 14 кейсов `pass`**, в `report.md` строка «All executed cases passed.»

Smoke: `pass` у T1, T10, T11, T13, остальные — `skip` с причиной. Если smoke падает, полный
режим запускать бессмысленно: проблема в запуске сервера или транспорте.

## Что прислать обратно

1. `packages/acp/acp/acceptance/report.md` — основной отчёт (таблица + stderr-хвост).
2. `packages/acp/acp/acceptance/report.json` — машинный отчёт.
3. Если что-то упало — дополнительно 20–30 строк stdout драйвера и текст ошибки.
4. Версию сервера из T1 и модель, если она упоминается в ошибке.

Ничего из `report.*` не содержит ключ: драйвер не печатает окружение.

## Диагностика

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| T1 timeout (60 с) | медленный старт `tsx`/сборки исходников | повторить один раз; при повторе — `ACP_ACCEPTANCE_TIMEOUT_MS=900000` |
| T2 fail с HTTP 401 | ключ не проброшен в дочерний процесс | проверить, что `DEEPSEEK_API_KEY` виден в окружении запуска |
| T2 fail с unknown model | в профиле `acp` модель `deepseek-v4-flash` недоступна | сообщить точный текст ошибки; это ограничение стенда, не теста |
| T6 fail «no title» | заголовок не успел записаться в кэш | повторить прогон; драйвер уже ждёт до 15 с |
| T9/T10 fail «unexpected error: …» | изменился текст диагностики | приложить полный текст — это регрессия контракта |
| Сервер не стартует | нет `node_modules`/`tsx` | выполнить `pnpm install` в корне |

## Ограничения сценария

- Recorded snapshot (keyless replay) сюда не входит: для записи нужен ключ и отдельный
  сценарий в `snapshots/acp`, это следующий шаг.
- Разрешения (permission prompts) и инструменты не проверяются: промпты текстовые,
  чтобы прогон был детерминированным.
